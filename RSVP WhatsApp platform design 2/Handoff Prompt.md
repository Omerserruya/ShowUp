# פרומפט ל-Claude Code: עדכון ShowUp לפי העיצובים

מצורפת תיקיית עיצובים של ShowUp (קבצי HTML שנפתחים ישירות בדפדפן, יחד עם `support.js` ותיקיית `assets/`). המשימה: לעדכן את המוצר האמיתי שלנו כך שייראה ויתנהג כמו העיצובים, **בלי להמציא יכולות שאין למערכת**.

## קבצי המקור (Source of truth לעיצוב)
| מה בונים | קובץ עיצוב |
|---|---|
| דף נחיתה / עמוד ראשי | `ShowUp Landing v6.dc.html` |
| מערכת (דשבורד מארח, דסקטופ) | `ShowUp Platform v6.dc.html` (בית, אורחים, סבב שליחה, שולחנות, מצב, הגדרות) |
| הרשמה ופתיחת אירוע | `ShowUp Event Signup v2.dc.html` (חבילה → פרטי אירוע → הודעות → תשלום → האירוע נפתח) |
| מובייל, כל הזרימות | `ShowUp Mobile Flows.dc.html` (45 מסכים, 8 קבוצות + קבוצת 00 הרשמה) |

פתחו כל קובץ בדפדפן כדי לראות אותו. כל העיצוב כתוב כ-inline styles, אז את הערכים המדויקים (צבעים, ריווח, רדיוסים, גדלי טקסט) קוראים ישירות מה-markup. הלוגיקה (מצבים, טקסטים דינמיים) נמצאת ב-`<script data-dc-script>` בתחתית כל קובץ, בתוך `renderVals()`.

## שלב 0: לפני שנוגעים בקוד (חובה)
1. מפו את הקוד הקיים: frontend, backend, שירות שליחת הוואטסאפ, webhook, מודל הנתונים וה-endpoints הקיימים.
2. צרו קובץ `DESIGN_GAP.md` עם טבלה: **כל מסך ורכיב בעיצוב ← מה קיים היום ב-API/DB ← סטטוס** (קיים / קיים חלקית / לא קיים).
3. **עצרו והציגו לי את הטבלה לפני שמתחילים לבנות.** אני מחליט מה נבנה עכשיו, מה מוסתר ומה נדחה.

## כללי ברזל
- **אסור להמציא API, שדות או יכולות.** כל נתון שמוצג חייב להגיע מ-endpoint שקיים בפועל, או משדה שאפשר לחשב ממה שקיים.
- **שכבת גישור (adapter):** אם מבנה הנתונים הקיים שונה ממה שהעיצוב צריך, כתבו שכבת מיפוי בצד ה-frontend, למשל `src/adapters/`. לא משנים את ה-API בלי אישור.
- **רכיב בעיצוב שאין לו גיבוי במערכת:** לא מזייפים נתונים. מסתירים אותו מאחורי feature flag, או מציגים מצב ריק כן ("בקרוב"), ומתעדים ב-`DESIGN_GAP.md`.
- **לא שוברים זרימות קיימות.** כל מה שעובד היום ממשיך לעבוד: התחברות, שליחת תבניות וואטסאפ, קליטת תשובות ב-webhook ותשלום.
- תבניות וואטסאפ: משתמשים רק בתבניות מאושרות שקיימות במערכת ובמבנה הפרמטרים הקיים. נוסח שמופיע בעיצוב ואין לו תבנית מאושרת הוא הצעה בלבד. מסמנים אותו ב-`DESIGN_GAP.md` ולא שולחים אותו.

## שפה עיצובית (לחלץ ל-design tokens משותפים)
- רקע נייר `#FAF8F4` / `#F5F1E9`, כרטיסים לבנים עם גבול חם `#E8E3D9` / `#E3DED4`, טקסט `#16150F`, טקסט משני `#4A4741` / `#5B564D`.
- מותג: לבנדר `#C9B8F3` לכפתורים ראשיים (טקסט כהה), סגול עמוק `#5A3DA6` לקישורים ולהדגשות, `#432C85` ל-hover, רקעי tint `#F6F2FD` / `#DCD0F4`.
- **אין משטחים שחורים.** שחור רק לטקסט.
- פונט Heebo (600 לכותרות), אייקונים Material Symbols Rounded.
- RTL מלא (`dir="rtl"`), עברית פשוטה, בלי ז'רגון טכני ובלי אימוג'י בממשק (מותר בתוך תוכן הודעות וואטסאפ).
- ניגודיות טקסט מינימלית 4.5:1. אזורי לחיצה במובייל לפחות 44px.
- מומלץ לממש את ה-tokens כ-theme אחד, כך ששינוי צבע או ריווח יחול על כל המסכים.

## דגשים לכל חלק
**דף נחיתה:** הירו בהיר: כותרת, טופס "יאללה, מתחילים" וצ'אט וואטסאפ מונפש בלולאה, ואז מה מקבלים, איך זה עובד (ציר 01–04), העוזר, תעריפים (Basic ₪39 / Plus ₪99 / Pro ₪199), אמון, שאלות, CTA ו-footer. הכפתור "שלחו לי הזמנה לדוגמה" עובד רק אם יש endpoint לשליחת דמו. אם אין, מציגים אותו כ-disabled ומתעדים.

**מערכת:** מציגים רק את מה שמארח צריך: כמה מגיעים, כמה מנות מכל סוג, למי להתקשר ומה לעשות השבוע. לא מציגים זמני תגובה, קודי תבנית, מפתחות API או ספירות קריאה. ייבוא אורחים מוואטסאפ: איש קשר ששותף נכנס ל"ממתינים לאישור" (אישור / עריכה) ורק אחר כך מתווסף לרשימה. אם ה-backend לא תומך בתור ממתינים, זה פער שמתעדים ולא ממציאים.

**הרשמה:** 4 שלבים עם סרגל התקדמות. סוג אירוע ← שדות מותאמים (כלה וחתן, חתן וחתן, כלה וכלה, בר/בת מצווה וכו'). לוח שליחה לפי תאריך האירוע. תשלום דרך ספק התשלום הקיים בלבד.

**מובייל:** לפי `ShowUp Mobile Flows.dc.html`. הושבה מוצגת כרשימה עם פסי מילוי, לא כמפת אולם.

## סתירות ידועות שצריך להכריע בהן (שאלו אותי, אל תנחשו)
1. **מחירים:** בדף הנחיתה ₪39/₪99/₪199 (מהאתר החי). בזרימת ההרשמה ובמובייל ₪249/₪449/₪690. המחירים האמיתיים הם אלה שבמערכת התשלום.
2. **טענות שיווקיות לאימות:** החזר כספי מלא תוך 14 יום, מספר וואטסאפ עסקי רשמי, פרטי האשראי לא נשמרים, סבבי הודעות לכל חבילה.
3. **"העוזר" (פקודות בשפה חופשית בוואטסאפ):** האם קיים, ומה הוא יודע לעשות בפועל? מציגים רק פקודות שבאמת עובדות.
4. **ההמלצה והתמונה בדף הנחיתה הן placeholder.** לא עולים לאוויר בלי המלצה אמיתית.

## תוצרים
1. `DESIGN_GAP.md`: טבלת פערים (לאישור לפני שבונים).
2. Theme / design tokens משותפים.
3. דף נחיתה, הרשמה, מערכת ומובייל מעודכנים, כולל responsive.
4. שכבת adapters לכל מקום שבו העיצוב והנתונים לא תואמים.
5. רשימת feature flags ומה מוסתר מאחוריהם.
6. סיכום קצר: מה נבנה, מה הוסתר, ומה דורש החלטה שלי.

עבדו בשלבים: נחיתה ← הרשמה ← מערכת ← מובייל. אחרי כל שלב עוצרים לבדיקה שלי.
